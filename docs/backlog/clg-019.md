# [CLG-019] bind: a Python binding and Python mocks for C code

## Summary

As a developer who tests C code from Python through a shared library, I want clanguru to generate a `ctypes` binding of what the code defines and Python mocks for what it calls but does not define, so that I write my tests and mocks in Python without declaring C signatures by hand.

## Description

A shared library exports symbol names only, so a Python caller has to write each function's `argtypes` and `restype` by hand, and they drift from the C code. The functions the code calls but does not define must be resolved too; `clanguru mock` fills them with gmock classes, which Python cannot drive. clanguru already has every stage this needs: symbols from `nm` on a partial-link object, declarations from libclang with the compilation database, and Jinja templates. yanga's pytest test framework (YANGA-013) is the first user.

## Scope decisions

- **Missing functions are mocked in Python.** For every function a test scope calls but does not define, a generated C function (a trampoline) forwards the call to a Python callable the test sets, for example a `unittest.mock.Mock`. Hand-written C fakes in `mockup_sources` stay possible for any function a trampoline cannot forward. Rejected: gmock mocks with their default action, because Python cannot set them; generated C stubs with counters and return values, because every hard case (a value per call, out-parameters, callbacks) would need its own C design, which `unittest.mock` already gives in Python.
- **clanguru generates the Python binding and the Python mocks, with the templates in clanguru.** A shared library holds no types, so the declarations come from the C sources; clanguru already parses them with the project's compile database. The templates belong to clanguru, like the gmock templates, because anyone who needs a Python binding for C code can use them, not only yanga. Rejected: hand-written bindings (as SPLedY's `spled_lib.py`), third-party generators (ctypesgen, cffi), and templates shipped by yanga.
- **The speed of `clanguru mock` does not change.** The extra type detail the binding needs is computed only for the new output. `bind` parses the sources once per test scope.
- **A new command `clanguru bind`, beside `mock`.** It writes, for one partial-link object, a Python binding of the symbols the scope defines and a C file of Python mocks for the functions it calls but does not define. It takes the same input options as `mock` (`--source-file`, `--partial-object-file`, `--compilation-database`, `--output-dir`, `--filename`, `--exclude-symbol-pattern`, `--strict/--no-strict` with the same default as `mock`) and `--library-name`. It has no `--symbol`, `--mock-type` or `--config-file`, which have no user for `bind`. Its templates are inside clanguru, like the gmock templates. Rejected: a `render` command with a template folder, because the folder has no user today; `mock --mock-type python`, because a binding is not a mock.
- **What `bind` writes.** `<filename>.py`: the binding, with `load(path=None)`, which without a path loads the library named by `--library-name` from the module's own folder, with no `lib` prefix and the extension chosen when it runs (`.dll` on Windows, `.dylib` on macOS, `.so` otherwise); it declares the defined functions and variables, the structs and enums they use, one Python mock slot per undefined function (`lib.mocks.<function> = Mock(...)`), and each undefined variable so a test can set it. `<filename>_mocks.c`: one trampoline per undefined function and a zero-initialised definition of each undefined variable, as the gmock renderer defines them; without them the library does not link on macOS and Windows. `<filename>.log`: the unsupported symbols, as `mock` writes today. Each trampoline reads an exported callback slot `clanguru_mock_<function>` and counts calls with no callback in `clanguru_unexpected_<function>`; the binding sets the slots and builds `unexpected_calls` from the counters. The `clanguru_` prefix keeps these names apart from the project's symbols.
- **`bind` chooses symbols exactly as `mock` does,** with the same code: every undefined symbol whose declaration clanguru finds, minus the `--exclude-symbol-pattern` matches. In strict mode `bind` fails only when an undefined symbol has no declaration, because the library cannot link then; unsupported types never fail and go to the log; a defined symbol without a declaration (for example from `mockup_sources`) is left out of the binding and listed in the log. The `bind` docs state these rules. Rejected: `mock`'s strict check, which also fails on unsupported types and so contradicts the log. Today this is split between `main.py` (the `nm` call) and `MocksGenerator.generate` (patterns, declarations); it moves into one function both commands call. That function does the selection; each command keeps its own strict check. `bind` requires `--partial-object-file`, since it has no `--symbol`. Choosing the defined symbols for the binding is new code in that function, with the same patterns and declaration lookup. Rejected: own selection rules for `bind`, because the two commands would then mock different things for the same code. A filter by project folder does not exist in `mock` today and is not added here.
- **C types in the first version.** Functions and variables with scalar, pointer, struct and enum types. Not yet: function pointers, unions, bit fields, variadic functions, and functions that return a struct by value, because a `ctypes` callback cannot return a struct. A function with an unsupported type gets no Python mock and is listed in the log; the user writes a C fake in `mockup_sources`, or the link fails and names it. The test library links with `-Wl,-z,defs` on Linux, which otherwise accepts missing symbols and fails only when the library is loaded.
- **A call with no Python mock set** returns a zero-initialised value of the return type and is recorded; the binding offers the list as `lib.mocks.unexpected_calls`. A test checks it if it wants. Rejected: failing the test automatically, because that needs a pytest plugin.
- **ctypes.** The binding and the Python mocks use `ctypes` from the standard library. Rejected: cffi and a compiled extension, because they need a second compiler setup; SPLedY already uses ctypes.
- **The test imports the binding; the binding loads the library next to it.** yanga writes the test library and the binding into the test scope's build folder and puts that folder on `PYTHONPATH` when it runs pytest. Rejected: an environment variable with the library path, which the binding makes unnecessary, and a pytest plugin with a fixture, which needs an installed package and gives nothing more today.
- **File names in the test scope's build folder.** For the test scope `light_controller`, yanga calls `clanguru bind --filename light_controller_binding --library-name light_controller_pytest`. The folder holds `light_controller_pytest.dylib` (`.so`, `.dll`), `light_controller_binding.py`, `light_controller_binding_mocks.c` and `light_controller_pytest_junit.xml`. The `_binding` suffix keeps the module name apart from any test file or component name.
- **Compiler for the tests.** clanguru and yanga install clang with a `PoksInstall` step (`pypeline.steps.poks_install`) in their `pypeline.yaml`, from the same poks bucket as SPLedY's `poks.json`, and their tests that build C use it; no test is skipped for a missing compiler. The step runs in CI: clanguru's `.github/workflows/ci.yml` lists it and requires `pypeline-runner>=1.28`, where `PoksInstall` exists; yanga puts it into `pipeline/test.yaml`, which its CI runs. yanga's gcov check also runs with gcc on Ubuntu, because SPLedY's gtest platform builds with gcc.
- **New words, where they are defined.** No repository has a glossary file. *Test scope* and *test library* are yanga's words and go into yanga's `docs/explanation/concepts.md`. *Binding* and *Python mock* are clanguru's words and go into the `bind` section of clanguru's `docs/features/index.md`. Drafts are in the folder of the item that adds the word and land with its implementation.
- **Order and release.** clanguru `bind` first, released. YANGA-012 in parallel, as it does not need clanguru. Then the yanga pytest generator, blocked by both. Then SPLedY, with editable installs of clanguru and yanga, before the yanga release; yanga is released only when SPLedY is green.
- **The items of the earlier planning run are removed.** CLG-017 and SPLED-005 are deleted by a `docs(backlog)` commit each, since their origin commits have work on top; YANGA-010 and a duplicate local clanguru commit were dropped when the local `main` branches were reset to origin. New items get new IDs.
- **CLG-017 is kept and set Superseded by CLG-019, not deleted** (the human, 2026-11-24, in the review of the SB-009 epic run). An item that was pushed in a commit that cannot be amended stays, so that no ID looks skipped. This replaces the deletion of CLG-017 in the decision above.
- **The compiler query runs only a gcc or clang driver** (the human, 2026-11-24). clanguru runs only a program whose file name is `gcc`, `g++`, `cc`, `c++`, `clang` or `clang++`, with an optional cross prefix and version suffix. The limit stops mistakes, not a hostile compile database; the build already runs the same compiler.

## What users see

- **New CLI command `clanguru bind`** with `--source-file`, `--partial-object-file`, `--compilation-database`, `--output-dir`, `--filename`, `--library-name`, `--exclude-symbol-pattern` and `--strict/--no-strict`. Not breaking: new command, `mock` options unchanged. UAT: yes. Why nothing existing does it: `mock` writes only gmock C++ classes, which Python cannot drive, and a binding is not a mock. Approved by the human (2026-11-24)
- **Public API of the generated binding module**: `load(path=None)`, `lib.mocks.<function>` (set a Python callable), `lib.mocks.unexpected_calls`. Not breaking: new. UAT: yes, through the SPLedY tests. Why: nothing generates ctypes declarations today; SPLedY writes them by hand. Approved by the human (2026-11-24)
- **The parser asks the compiler for its system headers** for every command that parses (`docs`, `mock`, `parse`, `bind`): when a compile command names a gcc or clang driver (`gcc`, `arm-none-eabi-gcc`, `clang++`, `cc`, with an optional version suffix), clanguru runs it as `<compiler> -E -v -x c|c++ <null device>` once per compiler and language, and passes every system include folder it prints to libclang after the command's own options: as `-isystem`, or as `-iframework` for a folder clang marks as a framework directory. The compiler's own builtin headers (`stddef.h`, `stdbool.h`) are kept too, since libclang from pip ships none. A gcc or clang compile command never names these folders, and libclang does not know them. The check is by file name only: a program named like a gcc or clang driver is run wherever it lives, any other program a compile database names is never run. Without a compilation database, or when the compiler cannot be run or prints no search list, nothing is added. Behaviour change on every system where a system header such as `stdint.h` was not found before (for example macOS, or a cross compiler's own headers): libclang typed what it declares as `int`; now the parser sees the real types (`uint8_t` instead of `int`). For the same input `mock` can write different types into its mocks and a different log, and passes strict mode where it failed on the parse error; `parse` also lists the declarations of the system header; `docs` output stays the same, since it copies the source text. Where the system headers were found before, the parse now reads the compiler's system folders first (for example `/usr/include` of the compiler's target, and gcc's own builtin headers), which matches what the compiler builds. Not breaking: the change replaces the `int` that a missing system header left with the real type. The criterion that `mock` writes the same files as before holds for input whose system headers were found before (its check, the existing mock tests, passes); on SPLedY's light_controller the `mock` time stays within 6% and its `.h`/`.cc` stay identical. UAT: yes, through the SPLedY tests. Why: libclang from pip knows neither the macOS SDK nor a cross compiler's headers, so `bind` lost structs with `uint8_t` fields. Fix round from the SB-009 integration, approved by the human (2026-11-24); the compiler query replaces a first macOS-only fix with `xcrun` (the human's decision after review, 2026-11-24)
- **Domain terms *binding* and *Python mock*** in clanguru's feature docs. Not breaking. UAT: no. Why: new concepts with no word yet. Approved by the human (2026-11-24)
