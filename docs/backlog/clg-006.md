# [CLG-006] Format-neutral trace blocks for sphinx-needs items

**Status**: Open
**Priority**: Low
**Component**: `src/clanguru/doc_generator.py`

**Summary**:
As an author of C/C++ doc comments, I want one block for a sphinx-needs item that works for RST and MyST output, so that I don't rewrite my comments when I switch the output format.

**Description**:
Today a needs item in a comment is written in the output syntax, as an RST directive or a MyST fence inside a `@docs`, `@rst` or `@md` block. A new `@trace` block describes the item in a generic syntax, and the formatter renders it as an RST directive or a MyST fence.

```c
/**
 * @trace Debounce door switch
 * type: impl
 * id: SWIMPL_DS-001
 * implements: SWDD_DS-100
 */
```

- The first line is the title. `key: value` option lines follow.
- The trace ends at the first empty line, at `@enddocs`, or at the end of the comment. There is no end tag.
- A line indented deeper than the keys continues the previous value, for long link lists.
- `type` is the directive name. Any name is accepted; clanguru does not read the project's `needs_types`.
- Type and links stay separate options, because a link name does not tell the type. In SPLed, `implements` links an impl to a spec and also a req to the architecture.
- A trace has no content. None of the 39 traces in SPLed's code has any. An optional end tag for content can come later without breaking this form.
- A `@trace` block is taken over inside or outside a `@docs` block. Only `@docs`, `@md`, `@rst` and `@trace` blocks reach the output. All other comment text is ignored.
- Jinja templating runs before the translation, as it does for the other blocks.
- A trace without `type`, or with a line that is neither `key: value` nor a continuation, stops the run with an error that names the declaration.
- Plain Markdown output gets the same fence as MyST.

**Acceptance Criteria**:
- [ ] A `@trace` block renders as a valid RST directive in RST output
- [ ] The same block renders as a valid MyST directive in MyST output
- [ ] A `@trace` block works inside and outside a `@docs` block, in source order
- [ ] An indented line continues the previous option value
- [ ] Jinja placeholders inside the block are resolved
- [ ] A malformed block fails with an error that names the declaration
- [ ] The block is documented
- [ ] All existing tests continue to pass
