# [CLG-009] Doc blocks from the function declaration in the header

**Status**: Done
**Priority**: Medium
**Component**: `src/clanguru/doc_generator.py`, `src/clanguru/cparser.py`

**Summary**:
As an author of C/C++ doc comments, I want `docs` to read the comment above a function's declaration in the header, so that I can keep the description and the traceability next to the interface.

**Description**:
Today `docs` reads `@docs`, `@md`, `@rst` and `@trace` blocks only from the comments directly above the function definition in the source file. Many projects write the function comment and the traceability next to the prototype in the header:

```c
/* foo.h */
/** @docs Calculates the checksum. @enddocs
 *  @trace {{ ... }} */
uint8_t Foo_Checksum(const uint8_t *data, size_t length);
```

```c
/* foo.c */
#include "foo.h"
uint8_t Foo_Checksum(const uint8_t *data, size_t length) { ... }
```

The definition in `foo.c` has no comment, so its section has only the code. The blocks in `foo.h` are lost without a message.

Cause: `CLangParser.search_description` walks back from the definition's first token in the source file. The tokens come only from the main file, so the header is never read.

**Acceptance Criteria**:
- [x] Blocks in a comment directly above a function declaration in an included header appear in that function's section
- [x] A function with comments above both the declaration and the definition gets both, declaration first
- [x] A function with no comment above its declaration produces the same output as today
- [x] Errors in a header block name the header path relative to the source file and the line of the comment
- [x] The behaviour is documented
- [x] All existing tests continue to pass

**Decisions**:
- Any header that declares the function counts. There is no filter for system headers: they have no tagged blocks, and a header is only read when it declares a function defined in the source file.
- When several headers declare the function, the blocks of all of them are used, in the order of the declarations (include order).
- Header blocks are rendered with the same context as the definition, including `gtest`. In practice a test has no prototype.
- A prototype in the source file itself is not a header declaration. Its blocks stay free blocks (see CLG-007), so nothing is emitted twice.
- Only top-level functions are covered, like `CLangParser.get_functions`. Classes and functions in namespaces are out of scope.
- Known limit: in a C++ source, prototypes inside `extern "C"` sit under a `LINKAGE_SPEC` node and are not read. Follow-up: CLG-010.
- The declarations are found in one pass over the top-level nodes of the translation unit: a `FUNCTION_DECL` that is not a definition, whose `canonical` cursor is the one of an emitted definition and that is located in another file. The result maps the canonical cursor to the descriptions.
- Each header with such a declaration is tokenized once, with `TranslationUnit.get_extent` over the whole file. `search_description` collects the comments directly above the declaration's first token.
- Errors name the header path relative to the folder of the source file, with `/` separators, so two headers with the same name stay apart. When there is no relative path (another drive on Windows), the absolute path is used.

**Tasks**:
1. Find the comments above header declarations. File: `src/clanguru/cparser.py`.
   - `_extract_tokens` takes raw tokens, so header tokens reuse it. `_collect_node_tokens` becomes static.
   - Add `CLangParser.get_declaration_descriptions(tu, functions)`. It maps the canonical cursor of each function to one list of comment tokens per declaration in another file, in one pass, and tokenizes each header once.
2. Put the header blocks in the function section. File: `src/clanguru/doc_generator.py`.
   - `_build_declaration_section` takes the declaration descriptions and collects them first, with the header path relative to the source as the name for errors.
3. Tests. File: `tests/test_doc_generator.py`.
   - Parametrized: header `@docs` block only, header `@trace` block only, header and source block, source block only.
   - A function declared in two headers gets the blocks of both, in include order.
   - A block above a prototype in the source file stays free.
   - A malformed `@trace` in the header names the header path relative to the source and the line, parametrized over a header beside and above the source folder.
   - The relative path falls back to the absolute path on another drive.
4. Document it. File: `docs/features/index.md`, "Blocks in the header".
