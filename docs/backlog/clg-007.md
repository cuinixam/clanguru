# [CLG-007] `@docs` blocks in any comment of the file

**Status**: Done
**Priority**: Low
**Component**: `src/clanguru/doc_generator.py`, `src/clanguru/cparser.py`

**Summary**:
As an author of C/C++ doc comments, I want `@docs` blocks to work in any comment of the file, so that I can document the file or a group of functions, not only a single declaration.

**Description**:
Today `docs` reads `@docs`, `@md` and `@rst` blocks only from the comments directly above a declaration. A block anywhere else in the file is ignored without a message. The change scans all comments of the file once and emits the blocks in source order. A block above a declaration must not be emitted twice.

**Acceptance Criteria**:
- [x] A `@docs` block in a file-level comment appears in the output, even when it is not above a function or class
- [x] Free blocks appear under the file title, before `Functions`, in source order
- [x] A block directly above an emitted function or class appears once, in that declaration's section
- [x] A block inside a function body or other code is ignored
- [x] A block in code that the preprocessor skips (`#if 0`, an `#ifdef` of a disabled feature) is ignored
- [x] A block that uses `gtest` but is not directly above a test fails with the line of the comment and a hint how to fix it
- [x] The behaviour is documented
- [x] All existing tests continue to pass

**Decisions**:
- A free block is a tagged block in a file-level comment that is not directly above an emitted function definition or class. Blocks above prototypes, variables, structs and typedefs are free; today they are lost without a message.
- Free blocks go under the file title, before `Functions`, in source order. Output for files without free blocks does not change.
- Comments inside function bodies, struct or class bodies and other code are ignored.
- Free blocks support `@md`, `@rst`, `@trace` and Jinja like declaration blocks. `gtest` is not set. Errors name the source file instead of a declaration.
- Known limit: a comment directly above the first function belongs to that function, even when it is meant as a file header. Blank lines do not separate them; code such as `#include` does.
- Comments in code that the preprocessor skips are ignored, like comments in function bodies. A variant documents only what it compiles. Found in SPLed: the Disco gtest report failed on `@trace {{ gtest.test }}` above a `TEST` inside `#ifdef CONFIG_BRIGHTNESS_ADJUSTMENT_AUTOMATIC`. The test is not compiled, so the comment became a free block, and free blocks have no `gtest`.
- The skipped ranges come from libclang's `clang_getAllSkippedRanges`. The Python bindings do not wrap it, so clanguru calls it through `clang.cindex.conf.lib` with ctypes. libclang records the ranges only with the parse option `PARSE_DETAILED_PROCESSING_RECORD`; without it the list is empty.
- That parse option also adds macro and `#include` cursors to the top level. `_extract_nodes` drops cursors whose kind is a preprocessing kind, so `tu.nodes` stays as it is today for `docs`, `mock` and `parse`.
- Known limit: a comment directly above an `#if` line is active code and stays a free block, even when the code under the `#if` is skipped. Put the block inside the `#if`.
- A block that uses `gtest` but has no test under it is an authoring mistake, not a clanguru defect, so it stays a `UserNotificationException`. Before the skipped-code fix, the same message came from a clanguru defect and gave the author nothing to act on. The causes left are: the comment stands above an `#if` line, other code stands between the comment and the test, the block is above a function that is not a test macro, or it is a file-level block. Every error names the line of the comment, and an undefined `gtest` adds a hint.
